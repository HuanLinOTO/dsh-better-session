# 数据与工作目录的 layout

状态：已实现。范围：`dshdev` 起的两种形态（dev / bundle）各自在哪些目录上落什么，以及 profile 从哪来。

## 运行多态：先定"形态 × 槽位"，再谈目录

同一套代码要在几种**形态**下跑，而每种形态下**每个槽位**落到哪儿是**固定**的。先把这张表钉死，后面所有的
"哪个目录里有什么"都是它的展开——不定死就会反复出"少服务 / 配置不生效 / 找不到模块"这类错。

- **形态**：`dev`（`dshdev web|desktop`）、`--prod`（起一次**打包形态的解析面**）、`bundle`（真打包，跑在用户机器上）。
- **槽位**：

  | 槽位 | 是什么 |
  | --- | --- |
  | **profileDir** | 装配根：清单（`dsh.profile.bundles`）、各 bundle 的 patch、**依赖面** |
  | **runtimeDir** | **工具链**：`node`、`pnpm`、TS 注册钩子——**不是**依赖面 |
  | **dataDir** | `$DSH_HOME`：`logs/`、会话库、凭据 |
  | **闭包根** | 官方 bundles 与 `dsh` 的解析锚点：`<闭包根>/node_modules/@deepseek-ai/dsh/package.json` |
  | **壳** | Electron app 目录（它**自己**的 `node_modules`） |
  | **buildCache** | 构建 / 打包缓存（随时可重建） |

| 槽位 | dev | `--prod` | bundle（运行期） |
| --- | --- | --- | --- |
| profileDir | `<workspace>`（app 目录本身） | `<buildCache>/deploy` | `$DSH_HOME/profiles/desktop` |
| runtimeDir | `<workspaceRoot>/node_modules/.pnpm` | `<buildCache>/deploy` | `Resources/runtime` |
| 闭包根 | 工作区 store | deploy 目录 | **profile 自己**（随包 tar 解出来的那份） |
| 壳 | `<buildCache>/shell` | 同 dev | `Resources/app` |
| dataDir | `<workspace>/.dsh-store` | 同 dev | 平台数据目录 + app 名（`xdg`） |
| buildCache | `<workspace>/node_modules/.dshdev` | 同 dev | 构建机上的 `.dshdev` |

### 依赖面只有三份，各司其职

历史上它们互相顶替过（profile 的依赖一度由 runtime 逐包 `link:`），代价是"少服务 / 配置不生效"：

| 份 | 位置 | 装什么 |
| --- | --- | --- |
| **壳** | `Resources/app/node_modules` | 壳自己的依赖（`@morlay/dsh-desktop-host`、`@deepseek-ai/dsh-app-boot`…） |
| **profile** | `$DSH_HOME/profiles/desktop/node_modules` | **行加载面**：官方 bundles + `dsh` + 全部传递依赖（随包 tar 解压出来的实体闭包） |
| **runtime** | `Resources/runtime` | **只有工具链**（`node` / `pnpm` / loader / `appconfig.json`），**没有** `node_modules` |

**加载仍交给上游 boot**：`@deepseek-ai/dsh-app-boot` 加 `dsh` 的安装根按 `dsh.profile.bundles` 逐行加载，而那些行
本身是上游包——所以 profile 那份闭包必须**完整**（实测 1119 个顶层包，与 `pnpm deploy --prod` 的产物同形）。
**闭包根（安装锚点）指向 profile**，不是 runtime；runtime 不再带闭包之后，锚点写错就会当场
`ENOENT: realpath …/runtime/node_modules/@deepseek-ai/dsh`。

## 三个不同的东西（别混）

| 名字           | 是什么                                                       | 谁读它                                            |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| **profileDir** | **profile 清单所在的目录**（`package.json` 的 `dsh` 段在这里） | 装配时按它解析 bundle 与插件面                    |
| **dataDir**    | **数据面根**（`$DSH_HOME`）：`logs/`、会话库、各种 store      | 宿主与上游各行按 `DSH_HOME` 读；壳的日志也落这里   |
| **buildCache** | **构建/打包的缓存目录**（不是运行时数据，随时可重建）         | `dshdev` 自己：装配壳、备 runtime、备 seed、放产物 |

三者互不嵌套是常态：dev 下 profileDir 与 buildCache 都在工作区里，dataDir 默认也在工作区里；bundle 运行期
profileDir 与 dataDir 同属 `$DSH_HOME`，buildCache 只属于构建机。

## dev（`dshdev web` / `dshdev desktop`）

| 目录          | 值                                              | 说明                                                                |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| workspace     | `apps/dsh-custom-next`（首个位置参数，缺省 cwd） | app 目录：`package.json` 的 `dsh` 段是装配输入                       |
| **profileDir** | `<workspace>`                                   | **dev 的 app 目录就是 profile 目录**（有 `dsh` 段的那份清单）         |
| **dataDir**   | `<workspace>/.dsh-store`（`--data-dir` 可换）    | `--data-dir=xdg` / `=env` / `=<绝对路径>`，与打包形态同一份解析规则   |
| **buildCache** | `<workspace>/node_modules/.dshdev`              | 见下                                                                |
| ↳ `shell/`    | 装配出的 **Electron app 目录**                   | 引导 + 转译后的 `dist/` + 清单 + 本地化；壳从这里启动                 |
| ↳ `development/` | dev 的 Electron `--user-data-dir`            | Chromium 自己的状态，与 dataDir 无关                                 |
| ↳ `runtime/`  | 随包的 node + TS loader + pnpm                  | 宿主子进程用它起                                                     |
| ↳ `seed/`、`deploy/` | 官方包的源码种子 / 部署面                 | "官方闭包"的两种落法                                                 |

**profileDir 的判据是形态**（`isDevForm()`，壳注入的 `DSH_DEV_FORM`）：dev 一律用 app 目录，只有**打包产物**
才用 `{dataDir}/profiles/desktop`。别用"那个目录有没有 package.json"之类的路径探测——`--data-dir` 可以把它指到
任何地方（XDG 里恰好也有个 `profiles/desktop`），探测会把 dev 误判成 bundle：根指到 profile、页面 404。

### 为什么不合成一份 profile

dev 的 profile root **就是 app 目录本身**（Electron 与 `web` 都一样）：装配清单与 patch 层本来就住在那里，
中间再合成一份只多一个会过期的事实。代价是插件页的安装 / 卸载会改 app 的 `package.json` 与工作区 lockfile
（那正是"这个目录就是 profile"的语义），这些运行时状态因此要 gitignore。

dev 的安装根就是工作区 pnpm store（`<workspaceRoot>/node_modules/.pnpm`，零复制、零镜像）：它的
`node_modules/` 是扁平 store，`import.meta.resolve('@deepseek-ai/dsh/package.json')`（cwd 在该目录下）解析到
`vendor/deepseek-harness/apps/cli/package.json`——即工作区源码面那份，正是 dev 要的。

### 两个形态的装配入口

| 形态            | profileDir | runtimeDir                     | boot 入口                                                          | overlay                                              |
| --------------- | ---------- | ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------- |
| dev（Electron） | app 目录   | `<workspaceRoot>/node_modules/.pnpm` | 宿主 [`src/index.ts`](../../../../packages/desktop/dsh-desktop-host/src/index.ts)（官方 `loadProfileDirectory` + `runProfile`） | 桌面 patch + [dev-only bundle](../../../../packages/bundles/web-custom-profile/package.json) |
| dev（web）      | app 目录   | 同上                            | 宿主的 web 入口 [`src/web.ts`](../../../../packages/desktop/dsh-desktop-host/src/web.ts) | 同一个 dev-only bundle                                |

只有 web 形态需要一条 dev 专用入口：上游 `dsh web` 会按 profile 名去 `$DSH_HOME/profiles/<name>` 找 profile，
而 dev 的 profile 在工作区的 app 目录里。装配本身仍复用上游那两步（`loadProfileDirectory` + `runProfile`）——
自己实现一遍等于把上游的兼容性检查、跳过清单上报、fail-loud、关停语义全部抄一遍并跟着版本走。

### dev 在 profile root 里留下的文件

| 文件                              | 谁写                               | gitignore（app 目录形态） |
| --------------------------------- | ---------------------------------- | ------------------------- |
| `cordis.yml`                      | `runProfile`（每次启动重写空根）    | 是                        |
| `compatibility.json`              | 插件版本豁免操作（设置面板 / CLI）  | 是                        |
| `.plugin-manager/`                | 插件页的包操作（安装记录、日志）    | 是                        |
| `node_modules/`、`pnpm-lock.yaml` | 包操作（dev 下就是工作区的）        | `node_modules/` 已有      |

## app 的 `dsh` 段：显式写清楚每一条依赖与形态

装配清单**显式**写在 app 的 `package.json` 里，工具不替它合并、不替它猜：

| 字段                          | 谁读                     | 语义                                                                 |
| ----------------------------- | ------------------------ | -------------------------------------------------------------------- |
| `dsh.version`                 | 打包                     | 官方包（`@deepseek-ai/*`）的版本基准，`officialDeploySpecs` 据此算出 spec |
| `dsh.profile.bundles`         | web 与桌面**都读**        | 两种形态共用的装配行                                                  |
| `dsh.desktop.profile.bundles` | 只有桌面（`desktop` / bundle） | **只写桌面独有的**，工具与上一条**合并**（按包名去重）；当前为空      |
| `dsh.desktop.dataDir`         | 桌面                     | 数据面根（`$DSH_HOME` 三态：`xdg` / `env` / 绝对路径）；旧名 `dshHome` |
| `dsh.desktop.{id,name,icon,window}` | 桌面               | 应用标识与窗口形态                                                    |
| `dsh.dev.exclude`             | dev                      | 哪些包按"非开发模块"预编译（见本文件末尾）                             |

"官方那一面"（`@deepseek-ai/dsh-base` / `dsh-web-app` 等）不是 app 的 npm 依赖，而是**装配行**：打包时
`installOfficialSurface` 用 `dsh.version` 把 `dsh.profile.bundles` 里的官方包解析成具体 spec，写进
**deploy 的中间清单**（不是源包），再在那个目录里装出来。app 自己的 `dependencies` 只管它真正 import 的包。

## bundle（`dshdev desktop bundle`，以及产物运行起来之后）

### 构建期：四步，各自只碰自己那段

| 步骤              | 产出                                   | 边界（只做这一件事）                                                                            |
| ----------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `prepareRuntime`  | `<buildCache>/runtime/`                 | 随包的 node、pnpm，以及**那份 TS 注册钩子**与它用到的两层依赖（`oxc-transform`、`@oxc-project/runtime`） |
| `prepareSeed`     | `<buildCache>/seed/`                    | 官方包的源码种子（打包形态的"官方闭包"由此离线装出来）                                            |
| `prepareShell`    | `<buildCache>/shell/`                   | **app 目录**：整包源码（`src`、原样清单、`locale`）、自动生成的入口 `main.mjs`，以及壳要用的宿主包 |
| `buildDesktopApp` | `<buildCache>/artifacts/mac-arm64/…`    | electron-builder 按 `files` / `extraResources` 把上面三样拼成 `.app`                              |

`files` 只列 app 目录里要进产物的那几项（`main.mjs`、`package.json`、`src/**`、`locale/*.json`）；
`extraResources` 负责 runtime、seed、appconfig 与**壳要用的那个宿主包**（放到 `app/node_modules/` 下——
app 目录自己的 `node_modules` 会被 electron-builder 的依赖收集规则改写，别用它）。

### 运行期：谁加载谁

```
Electron
  └─ Resources/app/main.mjs            ← 入口：报包根 → 挂 runtime 里的 ts-register → 按包名加载壳
       └─ Resources/app/src/index.ts    ← 壳（TS 源码，由注册钩子转译）
            ├─ 起宿主子进程：Resources/runtime/node --import <ts-register> <宿主源码>
            │    └─ profile = <dataDir>/profiles/desktop（随包 pnpm 离线装出来的那份）
            └─ 取 preload：GET http://app/@dsh/preload.cjs（宿主现场打成 CJS）→ 落盘 → 交给窗口
```

app 目录里**没有 `dist/`**：入口是生成的 `main.mjs`，业务是整包 `src/`，preload 的 CJS 由宿主现场打包。

运行期（用户机器上）：

| 目录           | 值                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------- |
| **profileDir** | `<dataDir>/profiles/desktop`                                                                  |
| **dataDir**    | `appconfig.dshHome` 解析：`xdg` → 平台数据目录 + app 名，`env` → 环境里的 `DSH_HOME`，或绝对路径 |
| app 目录       | `<Resources>/app`（`asar: false`，与 dev 的 `shell/` 结构一致）                                 |
| runtime、seed  | `<Resources>/runtime`、`<Resources>/seed`                                                      |

打包形态的 profile 依赖面由**随包 tar**解压而来：打包时把 deploy 的完整闭包打成
`seed/profiles/desktop/profile-node-modules.tar`（491MB；7023 个 symlink 全是相对的，解压到任意位置都不坏），
壳首启按 seed hash 解压进 `$DSH_HOME/profiles/desktop/node_modules`。profile 的清单保持**声明**原样（只有
`dsh.profile.bundles`）：壳**不再**往它里面写 `dependencies`，也**不再**写 `pnpm-workspace.yaml` 的 `overrides`，
更不在启动时跑一次 install——那套逐包 `link:` 不带传递依赖（少 959 个包），路径还钉死构建机。

`cordis.patch.yml` 是用户数据（重种豁免）。app 的 `dsh.profile.bundles` 是**声明**：dev 直接读它，打包由工具
按官方形态落成清单。

## 日志

两处日志同放 **`<dataDir>/logs/`**，对着看就能定位"页面 → 壳 → 宿主"断在哪一段：

- `shell.log`：壳写。启动那行是**一个形态的完整快照**：形态、根、`profileDir`、`dataDir` 与其取值来源、bundles 数
  ——[`index.ts`](../../../../packages/desktop/dsh-desktop-shell/src/index.ts)；
- `host.log`：宿主写（stdout/stderr 落一份盘）。打包形态 GUI 里看不到宿主输出，而"某个 bundle / 某一行没起来"
  的第一现场就在这里——[`host-process.ts`](../../../../packages/desktop/dsh-desktop-shell/src/host-process.ts)；
- `dev-host.log`：宿主写（`@morlay/dsh-client-modules` 的 dev 面）。

## 遗留

- 上游 `loadProfileDirectory` 会对清单里出现**已退役 bundle** 的 profile 回写 `package.json`（`RETIRED_BUNDLES`）。
  dev 形态下即回写源码目录里的 app 清单：只有在 app 真的列了那个包时才会发生。
- dev 的 profile root 是源目录，因此 `pnpm` 的包操作会写工作区清单与 lockfile。
